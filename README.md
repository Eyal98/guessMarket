# Guess Market — תרגיל 3

מימוש כאפליקציית **Client–Server** בסביבת Java 25.

מערכת מסחר באירועים, בהשראת Polymarket. **שרת Tomcat** מחזיק את מנוע המערכת וחושף את יכולותיו
כ‑endpoints של HTTP, ו**קליינטים של JavaFX** — כל משתמש מהמחשב שלו — מתחברים אליו, מעלים קבצי
אירועים, טוענים כסף לחשבונם וסוחרים. אף קליינט אינו מדבר עם קליינט אחר: כל המידע עובר דרך השרת,
וכל קליינט מושך ממנו את העדכונים פעמיים בשנייה.

## הוראות הרצה

### דרישת סביבה

**Java 25** (פותח ונבדק על JDK 25.0.4, Windows 11), ו‑**Tomcat 10.1 או 11**. השרת כתוב מול
`jakarta.servlet` ומקומפל מול Servlet API 6.0, ולכן אותו WAR רץ על שתי הגרסאות. הוא נבדק בפועל על
**Tomcat 10.1.60 ועל Tomcat 11.0.26**.

כל השאר נוסע עם ההגשה: ה‑WAR מכיל את המנוע ואת Gson, ותיקיית הקליינט מכילה את OkHttp, את Gson ואת
JavaFX. אין צורך להתקין דבר.

### מה יש בקובץ ההגשה

```
guess-market.war     השרת. WAR אחד בדיוק, לתיקיית webapps של Tomcat
client\              הקליינט: run.bat, ה-jar שלו, וכל ספריה שהוא צריך, כולל JavaFX
readme.docx          המסמך הזה
sample-files\        קבצי אירועים להעלאה, תקינים ותקולים, כולל אירועים מרובי אפשרויות
source\              קוד המקור וסקריפטי הבנייה, פרוסים כמו במאגר
```

### הרצת השרת

1. להעתיק את `guess-market.war` לתיקייה `webapps` של Tomcat.
2. להפעיל את Tomcat (`bin\startup.bat`). ה‑WAR נפרס אוטומטית תחת `/guess-market`.

כדי לוודא שהפריסה הצליחה: `http://localhost:8080/guess-market/` מציג עמוד קצר שאומר שהשרת רץ, ובו
רשימת כל ה‑endpoints.

### הרצת הקליינט

```
client\run.bat
```

הקליינט מוצא את השרת לבד, ב‑`http://localhost:8080/guess-market`, כפי שהתרגיל מתיר להניח. אפשר להפעיל
כמה קליינטים במקביל, כל אחד בחלון משלו ובשם משתמש משלו.

אם Tomcat רץ על פורט אחר, נותנים את כתובתו כארגומנט:

```
client\run.bat http://localhost:8081/guess-market
```

`run.bat` עובד מכל תיקייה, ובודק מראש שקיימת Java ושכל הקבצים במקומם — ומציג הודעה מובנת במקום
לקרוס בחריגה טכנית.

### בנייה מהמקור ובדיקות

`source\build.bat` בונה את ה‑WAR ואת תיקיית הקליינט, ו‑`source\test.bat` מריץ את הבדיקות. שניהם
משתמשים ב‑`javac` וב‑`jar` מה‑JDK בלבד, ודורשים את תיקיית `lib` כפי שהיא מתוארת במאגר:

| ספרייה | גרסה | תפקיד |
|---|---|---|
| `lib\javafx` | OpenJFX 25.0.4 | הממשק הגרפי |
| `lib\gson` | gson 2.14.0 | JSON בשני הצדדים |
| `lib\okhttp` | okhttp 4.9.1, okio 2.8.0, kotlin-stdlib 1.4.10, kotlin-stdlib-common 1.4.10, annotations 13.0 | ה‑HTTP client — חמשת ה‑jar שבשקף ההרצאה |
| `lib\servlet` | jakarta.servlet-api 6.0.0 | לקומפילציה בלבד; Tomcat מספק אותו בזמן ריצה |

## המסכים

הפריסה עוקבת אחר קובץ הסקיצה של תרגיל 3.

**התחברות:** שם בלבד — בלי סיסמה ובלי הרשמה, כפי שהתרגיל מבקש. שם שמישהו אחר מחובר בו נדחה, והסיבה
מוצגת ליד השדה. אחרי התחברות מוצלחת המשתמש מועבר למסך האירועים.

**לשונית Events:** כל האירועים שבשרת, מכל סוג ובכל מצב — שם, סטטוס, סוג, העמלה ומועדה, **חשבון
האירוע** וה‑MM — ומעליהם שלוש קבוצות מסננים שבכל אחת "All" נבחר מלכתחילה. מימין נפרש האירוע הנבחר:
אירוע LMSR מציג ערך לכל אפשרות והסטוריית מסחר, ואירוע ספר פקודות מציג ספר לכל אפשרות, את המחירים
שהם מרמזים עליהם, וטבלת המשתתפים. **מתחת לכותרת — לוח הפעולה** של המשתמש המחובר על האירוע.

**לשונית Account:** בראשה העלאת קובץ ונתיבו. משמאל, **שאר המשתמשים** — שם, יתרה, והאם הוא MM — ומתחתם
**שורות החשבון** של המשתמש עצמו, כל תנועת כסף בשורה משלה, עם היתרה וטעינת הכסף. מימין, כל האירועים
ומעמדו של המשתמש בכל אחד, חלקו באירוע שנבחר מתוכם, ואותו לוח פעולה שבלשונית האירועים.

**לשונית Chat:** הבונוס.

**שינוי גודל:** כל אזור שעלול לגלוש עטוף ב‑`ScrollPane` או ב‑`SplitPane`, הטבלאות מחלקות ביניהן את
הרוחב שיש להן, שורות ארוכות נשברות לשורה הבאה, והמסננים ולוח הפעולה עוברים שורה כשאין מקום. החלון
נותר בר‑שינוי גודל, והמינימום הוא 760×500 — נבדק בצילומי מסך שהכל נשאר שמיש בגודל הזה.

## מבנה המערכת — ארבעה מודולים

```
             HTTP + JSON                      קריאות Java
 client  <----------------->  server  ------------------------>  engine
 (JavaFX, OkHttp)            (servlets, Tomcat)                  (השוק עצמו)
     \                            |                                  |
      \___________________________|__________________________________/
                             dto  (הרשומות שעוברות בין כולם)
```

| מודול | תוצר | תפקיד |
|---|---|---|
| `dto` | `gm-dto.jar` | ה‑records שעוברים בין הצדדים. השרת כותב אותם כ‑JSON, והקליינט קורא אותם בחזרה לאותם טיפוסים בדיוק. |
| `engine` | `engine.jar` | השוק: אירועים, משתמשים, מסחר, קבצים. פסיבי לחלוטין, אינו יודע שיש HTTP, ובטוח לשימוש מכמה threads. |
| `server` | `guess-market.war` | servlets מעל המנוע. ה‑WAR מכיל את `engine.jar`, את `gm-dto.jar` ואת Gson. |
| `client` | `guess-market-client.jar` | הממשק הגרפי של תרגיל 2, שכל קריאה שלו למנוע הפכה לקריאת HTTP. **נושא את `gm-dto.jar` אך לא את המנוע.** |

**שימוש חוזר ברכיבים של תרגיל 2**, כפי שהתרגיל מבקש: מסכי תרגיל 2 עברו למודול הקליינט (ההיסטוריה שלהם
ב‑git נשמרה) ושמרו על צורתם — הטבלה והמסננים, פרישת האירוע לשני סוגיו, טבלת המעורבות, פאנל החלק
באירוע ו‑`Format`. מה שהשתנה הוא מקור הנתונים. ולוח הפעולה נכתב **פעם אחת** ומשמש בשני הקשרים, מתחת
לאירוע בלשונית האירועים ומתחת לאירוע הנבחר בלשונית החשבון.

## ה‑API של השרת

כל התשובות הן JSON. כל בקשה מלבד `/login` דורשת session מחובר; בקשה בלי session נענית ב‑**401**,
והקליינט חוזר למסך ההתחברות. בקשה שהשוק דוחה נענית ב‑**400** עם הסבר (`ErrorDto`), וקובץ שנדחה מביא
גם את כל תקלותיו אחת‑אחת.

| פעולה | כתובת | תשובה |
|---|---|---|
| POST | `/login?username=` | 200 המשתמש · 400 שם ריק · **409 שם בשימוש** |
| POST | `/logout` | |
| GET | `/users` | כל המשתמשים: שם, יתרה, האם MM |
| GET | `/account` | פרטי המשתמש המחובר — ורק שלו |
| GET | `/account/ledger?after=` | שורות החשבון שאחרי אלו שכבר אצל הקליינט |
| POST | `/account/deposit?amount=` | טעינת כסף |
| GET | `/events` | כל האירועים |
| POST | `/events/upload` | קובץ אירועים, multipart עם part בשם `file` |
| GET | `/events/lmsr?event=` · `/events/book?event=` | אירוע אחד במלואו |
| POST | `/events/open?event=` · `/events/close?event=&winner=` | פתיחה וסגירה, ל‑MM בלבד |
| POST | `/trade/buy` · `/trade/sell` · `/trade/order` | מסחר |
| GET / POST | `/chat?after=` · `/chat` | הבונוס |

**המשתמש לעולם אינו פרמטר.** השרת לוקח אותו מה‑session, כך שאין דרך לפעול בשמו של מישהו אחר.

## משיכת עדכונים

הקליינט מושך את השוק מהשרת **פעמיים בשנייה**, הקצב שהתרגיל מציע. שתי הטכניקות של ההרצאה משמשות, כל
אחת במקום שמתאים לה, כמו בדוגמת הצ'אט:

- **הכל, כל פעם** — לרשימות שמשתנות במקומן: האירועים, המשתמשים, ומעמדו של המשתמש עצמו. הן קצרות,
  ותשובה שלמה אינה יכולה לצאת מסנכרון עם השרת.
- **Delta** — לרשימות שרק מתארכות בסופן: שורות החשבון והצ'אט. הקליינט אומר כמה שורות כבר יש אצלו,
  ומקבל רק את השאר.

המשיכה רצה על `Timeline` של JavaFX, כך שכל סבב מתחיל על thread המסך; הבקשות עצמן אסינכרוניות לגמרי
(`enqueue` של OkHttp) ואינן מעכבות את המסך אף פעם. **ערך מתפרסם רק אם שונה מהקודם** — ה‑records
משווים לפי ערך — ולכן טבלה אינה נבנית מחדש, ואינה מאבדת את הבחירה בה, רק משום שעברה חצי שנייה. כל סוג
משיכה רץ לכל היותר פעם אחת בו‑זמנית: אם הגיע סבב בזמן שהתשובה הקודמת עוד בדרך, הוא נרשם ונשלח ברגע
שהיא מגיעה.

## המחלקות העיקריות החדשות

מה נוסף או השתנה בתרגיל זה, ומה תפקידו של כל דבר. הכוונה היא שיהיה אפשר להיכנס לקוד מכאן בלי לחפש.

| `MarketServlet` | הבסיס של כל servlet שפועל בשם משתמש מחובר: 401 למי שאינו מחובר, 400 עם הסבר השוק לכל סירוב. נכתב פעם אחת, כך שכל servlet הוא כמה שורות. |

## אירועים מרובי אפשרויות

אחת משתי מטרות התרגיל. נתמך בכל השכבות:

- **LMSR** נכתב מההתחלה לכל מספר אפשרויות. הסבסוד הוא `b·ln(n)`, וסכום הערכים תמיד 1.
- **ספר פקודות:** ספר לכל אפשרות. ה‑mint יוצר **סט שלם** — מניה חדשה אחת מכל אפשרות — ורק כשלכל
  אפשרות יש קונה, והמחירים שלהם יחד מגיעים ל‑`d`. רק סט שלם שווה תמיד בדיוק `d`, לא משנה מי זוכה;
  שני קונים של שתיים משלוש אפשרויות אינם יכולים לבצע mint, כי לזוכים באפשרות השלישית לא היה מי שישלם.
  ההזמנות הממתינות מקבלות את המחיר שביקשו, והנכנסת משלימה ל‑`d`. עבור שתי אפשרויות זה **בדיוק**
  הכלל שבנספח ב'.
- **המסך:** טבלאות האפשרויות והאחזקות גדלות לפי מספר האפשרויות, וספרי הפקודות נפרשים שניים בשורה.

`sample-files\three-options.xml` מכיל אירוע LMSR בן שלוש אפשרויות ואירוע ספר פקודות בן ארבע.

**שימו לב:** הסכמה של תרגיל 3 עדיין אומרת `maxOccurs="2"` לאפשרויות — היא הועתקה מתרגיל 2, כולל
שגיאות הכתיב שבתרשים. מאחר שהתרגיל מציין במפורש "תמיכה באירועים מרובי אפשרויות" כאחת משתי מטרותיו,
הטוען מקבל **שתיים או יותר**.

## הנחות והחלטות מימוש

כל מקום שבו התרגיל לא קבע במדויק, מופיעה כאן הבחירה שנעשתה והנימוק לה.

1. **Tomcat ו‑jakarta** — השקפים משתמשים ב‑`jakarta.servlet`. השרת מקומפל מול **Servlet API 6.0**
   ולא מול 6.1 של Tomcat 11, כך ש‑`javac` עצמו דוחה כל דבר ש‑Tomcat 10.1 אינו מכיר.

2. **HTTP client** — OkHttp 4.9.1 עם חמשת ה‑jar שבשקף, כמו בהרצאה, ו‑Gson בשני הצדדים.

3. **שם תפוס** — שם שמישהו **מחובר** בו כרגע. התנתקות, או session שפג, משחררים אותו, ומי שמתחבר בו
   שוב מוצא את החשבון בדיוק כפי שנשאר. כך המערכת מונעת שני קליינטים בשם אחד, שזו מטרת הכלל, בלי
   לנעול לתמיד שם של מי שסגר את החלון. ה‑session פג אחרי **שתי דקות** בלי בקשות; קליינט פעיל שולח
   בקשה פעמיים בשנייה ולכן לעולם אינו פג, וקליינט שנסגר בכוח משחרר את שמו תוך דקות. קליינט שנסגר
   כרגיל מתנתק מיד.

4. **משתמש מתחיל באפס** — אין יותר `initial-cash`. כל סכום חיובי ניתן לטעינה. **משתמש חסום אינו יכול
   לטעון כסף**: התרגיל קבע שמשתמש חסום אינו יכול לבצע **שום** פעולה, וטעינה היא פעולה.

5. **ספר החשבון** — קנייה אינה שורה אחת אלא עד שלוש: מחיר המניות, העמלה ששולמה, ובחשבון ה‑MM — העמלה
   שנתקבלה. כך נראית בחשבון גם תנועה שמישהו אחר גרם לה, כפי שהתרגיל מבקש. כך גם הפתיחה, הזכייה,
   עמלת הסגירה והיתרה שחוזרת ל‑MM.

6. **MM אינו משלם עמלה לעצמו** — עמלה היא הכנסתו של ה‑MM. כשהוא עצמו קונה באירוע שלו, או זוכה בו,
   העמלה אפס: אחרת היו בחשבונו שתי שורות שמבטלות זו את זו, "עמלה שנגבתה" שאיש לא שילם, ורווח או הפסד
   שסופר את הכנסתו כהוצאה. כסף של אף אחד אחר אינו זז אחרת.

7. **הקובץ לעולם אינו נכתב לדיסק** — התרגיל מזהיר שלשרת של הבודק אין הרשאת כתיבה. Tomcat כותב
   part גדול מסף מסוים לקובץ זמני, ולכן הסף הוגדר לגודל הקובץ המרבי (2MB): כל העלאה נשארת בזיכרון
   מתחילתה ועד סופה.

8. **בדיקות הקובץ** — הבדיקות של תרגיל 1, כפי שהתרגיל מבקש, ולא אלו של תרגיל 2: קובץ XML תקין, השורש,
   אירוע אחד לפחות, שם ותיאור, עמלה בין 0 ל‑90 וסוגה, לפחות שתי אפשרויות שונות, ושיטת מסחר תקינה. ועוד:
   **אין שם אירוע שכבר קיים** — לא בתוך הקובץ ולא בשוק — **בלי הבדל בין אות גדולה לקטנה**. כל התקלות
   מדווחות יחד.

9. **קבצים של תרגילים קודמים** נדחים בהודעה שאומרת זאת: `GM-users` שייך לתרגיל 2, ו‑`<id>` של אירוע
   שייך לתרגילים 1 ו‑2. קבלתם בשתיקה הייתה מסתירה שהקובץ בפורמט הלא נכון.

10. **DOCTYPE נדחה** — קבצים מגיעים עכשיו מהמחשבים של אנשים אחרים, ולקובץ כזה אין מה לבקש מהשרת
    לטעון קבצים אחרים או להרחיב ישויות בשמו. אף קובץ Guess Market אינו צריך DOCTYPE.

11. **מספר אירוע** — אירועים רק מתווספים ולעולם אינם נמחקים, ולכן מקומו של אירוע ברשימה הוא מספרו
    הקבוע כל עוד השרת רץ. השמות הם שמבדילים בין אירועים, והמספר הוא רק דרך קצרה להפנות אליהם בבקשה.

12. **"שאר המשתמשים"** — הטבלה מציגה את כל האחרים ולא את המשתמש עצמו, שפרטיו מוצגים בנפרד. **אין
    endpoint לפרטי משתמש אחר**: כל משתמש רואה את עצמו, ומהאחרים רק שם, יתרה והאם הם MM.

13. **מסחר משתי הלשוניות** — הסקיצה מראה "details and trade" בשתיהן. זהות המבצע כבר אינה שאלה: זה
    תמיד המשתמש המחובר, והשרת לוקח אותו מה‑session.

14. **המשיכה על `Timeline`** — ולא על `TimerTask` כבדוגמת הקורס. כך כל סבב מתחיל על thread המסך
    ויכול לבדוק מה מוצג, בלי מעבר בין threads; הבקשות עצמן אסינכרוניות כמו בקורס.

15. **הפעלה מחדש של השרת** — אין שמירה מעבר לחיי השרת, כפי שהתרגיל קובע. קליינט שהשרת כבר אינו מכיר
    (למשל אחרי שהשרת עלה מחדש) חוזר למסך ההתחברות עם הסבר.

16. **מה ירד מתרגיל 2** — העיצובים, האנימציות, הגרפים, יצירת אירוע, ושמירה וטעינה של מצב. הם לא נדרשים
    בתרגיל 3, ושמירה לקובץ אף אסורה על השרת. הם שמורים במלואם בתגית `ex2-submission`.

17. **נשאר מתרגילים קודמים** — `commission` ו‑`comision` מתקבלים שניהם; מכירה ב‑LMSR נתמכת; הזמנות
    של משתמש שנחסם נשארות בספר; ועמלת on-close נגבית מהסכום שמגיע לזוכים — **זו הנקודה היחידה שנותרה
    פתוחה לפרשנות**.

18. **DTO במודול משלו** — כפי שהומלץ בפורום, ה‑DTO יושבים ב‑`gm-dto.jar` נפרד שגם ה‑WAR וגם הקליינט
    מכירים, והקליינט **אינו מכיר את המנוע כלל**. הם records טהורים: אין בהם לוגיקה, אין בהם שום דבר
    של JavaFX, והמבנה שלהם שטוח ככל האפשר — שמות במקום הפניות, כך שאין מעגלים לסרלז.

19. **תיקון שנמצא בדרך** — בתרגיל 2, סגירת אירוע ספר פקודות מהמסך שילמה לזוכים כראוי ואז הציגה
    הודעת שגיאה, כי המנוע ניסה לתאר את האירוע הסגור בתיאור שמתאים ל‑LMSR בלבד. בתרגיל 3 הסגירה מחזירה
    את האירוע הסגור לשני הסוגים, ובדיקה נועלת זאת.

  וקניות מכמה threads בו‑זמנית, כשהסכומים חייבים לצאת מדויקים. בלי המנעול, בדיקת הקניות נכשלת בכל
  הרצה.
- **7 בדיקות של הקליינט מול שרת אמיתי**, על HTTP אמיתי: שם תפוס, 401 בלי התחברות, שרת שאינו קיים,
  המסלול כולו מהעלאה ועד קנייה, קובץ תקול, צ'אט, והתנתקות וחזרה. הן רצות כש‑`GM_SERVER` מצביע על
  שרת פעיל, ומדולגות בלעדיו.
- **9 בדיקות קליינט** שאינן צריכות שרת: תיאור מעמדו של משתמש באירוע; קובץ שאי אפשר לקרוא — שמדווח
  ככזה ולא כשרת שלא ענה; ו**כל DTO עובר הלוך‑חזור ב‑Gson ויוצא שווה בדיוק למה שנשלח**, מחזיק רק ערכים
  פשוטים, רשימות ו‑DTO אחרים — בלי מעגלים, בלי interface שהמפענח היה צריך לנחש לו מימוש, ובלי אף מתודה
  משלו.

המסכים עצמם אומתו בהרצה אוטומטית של הקליינט האמיתי מול Tomcat אמיתי, עם משתמש שני שפעל על השרת במקביל
וצילומי מסך בכל שלב. הצילומים תפסו שלושה דברים שבדיקה לא הייתה תופסת: ה‑MM ששילם עמלה לעצמו, תיאורים
בספר החשבון שנחתכו במקום להישבר, ועמודות שנדחקו מחוץ לטבלה צרה.

**ההגשה עצמה** נבדקה כפי שהבודק יפעיל אותה: ה‑zip נפרס לתיקייה שבשמה רווחים, ה‑WAR שבו הועתק ל‑Tomcat
11 חדש לגמרי ונפרס מעצמו, הקליינט שבו הופעל דרך `run.bat` מתיקיית עבודה אחרת, והמסלול כולו — התחברות,
העלאה, פתיחה, מסחר מול משתמש שני, צ'אט וסגירה — עבר מולו. גם `source` שבתוכו נבנה ועבר את הבדיקות.
הבדיקה חזרה במלואה, כולל הבדיקות מול שרת, על **Tomcat 10.1**.

**זליגת connections ב‑OkHttp** נבדקה במפורש: הקליינט הורץ 25 שניות של משיכה רצופה ופעולות, עם הלוגר של
OkHttp פתוח ברמת `FINE` ו‑garbage collection מאולץ — ולא הופיעה אף אזהרת "was leaked". כדי לוודא שהגלאי
באמת מסוגל להתריע בסביבה הזו, לקוח שלא סוגר את תשובותיו בכוונה הורץ לצדו, והאזהרה הופיעה מיד. בקוד
עצמו כל תשובה נסגרת: גוף התשובה נקרא בתוך try‑with‑resources, ותשובות שאין צורך בתוכנן (התנתקות) נסגרות
במפורש. שורת הלוגר עצמה אינה בקוד המוגש, כפי שהומלץ.
