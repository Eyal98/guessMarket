# Guess Market — תרגיל 4 (בונוס): קליינט WEB

קליינט **דפדפן** לשרת של תרגיל 3, שנבנה כולו בעבודה עם כלי AI. הוא עובד מול אותו שרת, **בדיוק באותם
ה‑API'ים** שהקליינט של JavaFX משתמש בהם, והשרת עצמו לא השתנה בשורה אחת. קליינט WEB וקליינט JavaFX
עובדים יחד על אותו שוק בו‑זמנית.

## כתובת הכניסה

**http://localhost:3000/**

`web\start.bat` פותח אותה בדפדפן לבד.

## הפעלה

1. **השרת** — מעתיקים את `guess-market.war` (ה‑WAR של תרגיל 3, ללא שינוי; הוא כלול בהגשה הזו) לתיקייה
   `webapps` של Tomcat ומפעילים את Tomcat (`bin\startup.bat`). אין שום שינוי בהקמת השרת או בתפעולו.
2. **הקליינט** — מריצים:

   ```
   web\start.bat
   ```

   הקובץ צריך רק את **Node.js** (18 ומעלה), ו**אינו מתקין דבר**: אין `npm install` ואין תלויות.
   הדפדפן נפתח על `http://localhost:3000/`, וחלון ה‑bat נשאר פתוח; סוגרים אותו כדי לעצור את הקליינט.
3. **Tomcat בכתובת אחרת, או פורט אחר לדף:**

   ```
   web\start.bat http://localhost:8081/guess-market 3001
   ```

4. **משתמש WEB נוסף** — דפדפן אחר או חלון פרטי (Incognito). דפדפן אחד הוא session אחד, ולכן משתמש אחד,
   בדיוק כמו קליינט JavaFX אחד.
5. **סגירת הלשונית** מנתקת את המשתמש מיד, כך שאפשר להתחבר באותו שם מקליינט JavaFX בלי לחכות שה‑session
   יפוג. **רענון הדף** משאיר את המשתמש מחובר.
6. **העלאת קבצי אירועים** נעשית מקליינט JavaFX של תרגיל 3 (`client\run.bat` מהגשת תרגיל 3), כי התרגיל
   מוציא את ההעלאה ממסך המשתמש של קליינט ה‑WEB. קבצים לדוגמה נמצאים ב‑`sample-files`.

## מה הקליינט עושה

ארבעה מסכים, כל אחד בנוי כמו המקביל לו בקליינט JavaFX — אותם חלקים, אותן עמודות, ואותם משפטים מילה
במילה:

- **התחברות** — שם בלבד. שם ריק, ארוך מ‑30 תווים, או שם שמישהו מחובר בו כרגע (409) — מוצגת הודעת השרת.
- **Events** — כל האירועים בשרת, עם שלוש קבוצות הסינון (סוג, מצב, עמלה) ושורת סיכום. בחירת אירוע מציגה
  אותו במלואו: באירוע LMSR — ערכי האפשרויות, החשבונות, היסטוריית המסחר והתוצאה; באירוע Order book —
  ספר הזמנות לכל אפשרות (קונים, מוכרים, Last/Bid/Ask/Mid/Spread) והמשתתפים. מתחת לכותרת — לוח המסחר:
  קנייה ומכירה ב‑LMSR, הזמנה ב‑Order book, ופתיחה וסגירה לעושה השוק.
- **Account** — שאר המשתמשים (שם, יתרה, האם MM), דף החשבון שורה לכל תנועה וטעינת כסף, כל האירועים
  ותפקידי בכל אחד, החלק שלי באירוע הנבחר, ואותו לוח מסחר. משתמש שיורד מתחת לאפס מקבל התראה, כמו
  ב‑JavaFX.
- **Chat** — הבונוס של תרגיל 3. **התרגיל אינו דורש אותו בקליינט ה‑WEB, והוא נשמר בכל זאת**: כולם רואים
  את מה שכולם כותבים, בין אם מ‑JavaFX ובין אם מהדפדפן.

הכל מתעדכן לבד פעמיים בשנייה, כמו ב‑JavaFX: מה שמשתמש אחר עושה מופיע אצל השאר תוך חצי שנייה.

**המראה** בהשראת **Polymarket**, האתר שהתרגיל כולו בהשראתו: משטחים לבנים, כחול אחד חזק לפעולה
העיקרית, ירוק לקנייה ואדום למכירה, מסננים בצורת "גלולות" וכרטיסים מעוגלים. המבנה עצמו — מה נמצא איפה —
נשאר זה של קליינט JavaFX, כפי שהתרגיל מבקש.

## איך זה בנוי

### למה יש שרת קטן ב‑Node

דפדפן שולח את עוגיית ה‑session של אתר רק לכתובת שממנה הגיע הדף. דף שמגיע מכל מקום אחר מלבד Tomcat יכול
לפנות ל‑Tomcat רק אם השרת מוסיף כותרות CORS — וזה שינוי בשרת, שהתרגיל אוסר. לשים את הדפים בתוך ה‑WAR היה
משנה את השרת גם כן.

לכן `serve.js` מגיש את הדף ב‑`http://localhost:3000/`, ומעביר כל בקשה תחת `/guess-market/` ל‑Tomcat כמו
שהיא, ואת תשובת Tomcat בחזרה כמו שהיא, כולל `Set-Cookie`. מבחינת הדפדפן הדף וה‑API הם כתובת אחת, עוגיית
ה‑session של Tomcat עובדת בלי שום שינוי, והשרת נשאר בדיוק כפי שהיה בתרגיל 3. ה‑relay אינו מכיר את ה‑API
בכלל, ולכן אינו יכול לסטות ממנו.

ה‑relay מאזין **רק למחשב עצמו** (127.0.0.1): הוא אינו פתוח לרשת, ולכן Windows אינו שואל אם לאפשר ל‑Node
לעבור את חומת האש. הוא מעביר רק נתיבים שנשארים בתוך `/guess-market` — נתיב עם `..` או `;`, שאצל Tomcat
היה מוביל ליישום אחר, נדחה.

## החלטות

1. **JavaScript רגיל, בלי framework ובלי build** — אין מה להתקין ואין שלב בנייה שיכול להיכשל אצל הבודק.
   כל מסך ממופה אחד לאחד לבקר של JavaFX.
2. **ה‑relay** — הדרך היחידה לתת לדפדפן לדבר עם השרת הקיים בלי לשנות אותו (ראו למעלה).
3. **טקסט לעולם אינו נכנס כ‑HTML** — שמות אירועים, שורות חשבון והודעות צ'אט נכתבים ע"י אנשים. אירוע בשם
   `<img src=x onerror=...>` מוצג כשם מוזר ולא רץ בדפדפן של אף אחד. בדיקה אוטומטית נכשלת אם קובץ כלשהו
   משתמש ב‑`innerHTML` וחבריו.
4. **לוח המסחר נבנה מחדש רק כשמה שאפשר לעשות משתנה** — האירוע, מצבו, האם אני ה‑MM, והאם אני חסום. מחירים
   ויתרות זזים פעמיים בשנייה, ובנייה מחדש איתם הייתה מוחקת כמות שהמשתמש באמצע להקליד. ממוקם במקום קבוע,
   כך שרענון אינו לוקח ממנו את הפוקוס.
5. **טבלה מתעדכנת במקום** — אותן שורות עם ערכים חדשים נכתבות לתוך השורות שעל המסך, כך שלחיצה שנחתה באמצע
   עדכון אינה הולכת לאיבוד.
6. **ניתוק בסגירת הלשונית, חיבור מחדש ברענון** — בסגירה הדף שולח beacon של logout, הבקשה היחידה שדפדפן
   עוד שולח כשדף נסגר. רענון שולח אותו beacon, ולכן השם נשמר בלשונית והדף המרוענן מתחבר מחדש לבד, פעם אחת.
7. **כסף נכתב כמו ב‑Java** — `%.2f` של Java מעגל חצי כלפי מעלה את הצורה העשרונית, ו‑`toFixed` של
   JavaScript מעגל את הערך הבינארי: 1.005 הוא "1.01" ב‑Java ו‑"1.00" ב‑JavaScript. `format.js` מעגל כמו
   Java, והבדיקות משוות למחרוזות שהדפיס Java עצמו.
8. **השרת משמיט שדות null** (Gson), ולכן אירוע שלא הוכרע מגיע **בלי** `winningOptionName` בכלל. הקוד בודק
   "חסר" ולא רק "null".
9. **שרת לא זמין** — באנר אדום עד שהשרת חוזר, בלי קריסה. בקשה שלא נענתה תוך 10 שניות נחשבת שלא נענתה,
   כמו ב‑OkHttp של JavaFX, כך שסוג משיכה אף פעם אינו נתקע. אם Tomcat הופעל מחדש ושכח את ה‑session,
   חוזרים למסך ההתחברות עם המשפט של JavaFX והשם כבר כתוב.
10. **אין פעולה כפולה** — כפתור שנשלח נשאר מושבת עד התשובה, ו‑Enter שנלחץ שוב (או מוחזק) בשדה הסכום או
   בצ'אט אינו טוען כסף או שולח הודעה פעם נוספת.

## עבודה עם כלי AI

**הכלי** — **Claude Code** של Anthropic, באפליקציית Claude לשולחן העבודה. בחרתי בו משתי סיבות: הוא בנה
איתי את תרגילים 1–3, ולכן כבר הכיר את הפרויקט ואת ה‑API של השרת; והוא עובד ישירות על המאגר — כותב קוד,
מריץ בדיקות, מפעיל את Tomcat ובודק את הדף בדפדפן בעצמו — ולא רק עונה בצ'אט. לא ניסיתי כלים אחרים לתרגיל
הזה.

**איך עבדנו** — קודם עיצוב: ה‑AI הציג את הדרישות כפי שהבין אותן ושאל את השאלות שהן החלטות שלי (JavaScript
רגיל או framework, האם ה‑WAR נכלל בהגשה). אחר כך מסמך עיצוב שאישרתי, תוכנית עבודה מפורטת, ורק אז מימוש,
כל חלק עם בדיקה שנכתבה ונכשלה לפני הקוד. באמצע העבודה ביקשתי שהמראה יהיה בהשראת Polymarket; ה‑AI פתח את
האתר, מדד ממנו צבעים, גופנים ופינות, ויישם אותם בלי לשנות את מבנה המסכים.

**היכן נדרשה התערבות** — ההחלטות היו שלי: הגישה, מה נכנס להגשה, שמירת הצ'אט, וכיוון העיצוב. בקוד עצמו לא
נגעתי. ה‑AI כן טעה כמה פעמים, ותפס את הטעויות בעצמו — בבדיקות או בבדיקה מול השרת האמיתי:

- המשיכה התחילה "טיק" אחד מאוחר מדי, והאות "השרת לא זמין" הבהב כשסוג משיכה אחד נכשל ואחר הצליח — שתי
  הבדיקות שנכתבו מראש נכשלו ותפסו את זה.
- "רווח או הפסד" הופיע על אירוע שעוד פעיל, כי השרת משמיט שדות null והקוד בדק null בלבד — נתפס בבדיקה מול
  השרת, ונוספה בדיקה שתופסת אותו.
- בסוף העבודה ה‑AI הפעיל בודק נפרד (סוכן נוסף שלא כתב את הקוד) על כל השינויים. הוא מצא שה‑relay האזין לכל הרשת
  (חלון חומת אש אצל הבודק), שלחיצה כפולה על Enter טוענת כסף פעמיים, ועוד כמה מקרי קצה — כולם תוקנו, כל אחד
  עם בדיקה שנכשלה לפני התיקון.
- טבלה שנבנתה מחדש בכל שינוי עלולה הייתה "לבלוע" לחיצה, ושדה מספרי מחק טקסט שגוי כך שהודעת השגיאה לא
  יכלה לצטט אותו — שניהם נתפסו בבדיקה בדפדפן ותוקנו.

לא הייתה דרישה שה‑AI לא הצליח לממש.
